| v2.10 | **M4 第六刀：向导把栈与栈的差别讲清楚（0.2.x）**：向导里原来只有栈的名字。现在新增**端口**（默认值**按栈的惯例**给：Vite 5173 / NestJS 3000 / Python 8000，可改；**用户改过就不会被换栈覆盖**）、**包管理器**（只在选了 Node 栈时出现 —— 给 FastAPI 选 pnpm 是"点了也没用的选项"）、以及每条选中栈的**现状标注**（官方脚手架：第一次要联网、失败自动回退内置骨架 / 内置模板：离线可用）。端口惯例由**服务端**的栈描述给出（不在前端写死第二份），并且**服务端再校验一次**（只收 1~65535 的整数：端口会被写进生成出来的代码，越界值等于交付一个"跑到一半才报错"的项目）。这一刀还记了一笔测试教训：e2e 先红了，查下去是**测试自己**把 8123 拼在 8000 后面（`page.type` 点击只定位光标不选中），产品是对的 —— 详情见 technical-design §43 |
| v2.11 | **M4 第七刀：技术栈拆成「维度」、每个栈各自的端口（0.2.x）**：向导改成**前端一行、后端一行**，各自选框架、各自一个端口（顺手修掉一个真 bug：上一版整个作业只有一个端口，双栈时前端 `vite.config.ts` 与后端 `app.listen()` 写的是**同一个号**，起服务必撞号）。技术栈按**维度**分开选：**框架**（Vue 3 / React / NestJS / FastAPI / Django，新增 **React**，走 Vite 官方脚手架 + 内置回退）、**语言**（TypeScript / JavaScript，两种语言的内置骨架都出 —— 选了 JS 不会拿到一份 TS）、**附加项**（Vue：Router / Pinia / ESLint / Prettier / Vitest / JSX；React：ESLint；NestJS：严格模式）。控件**照服务端的声明渲染**：这个栈不支持的维度就不出现，只有一个候选的维度（NestJS 的语言）显示成静态文字 —— 不做"点了也没用"的死控件。官方做不到的组合改成**换一条官方路并说明原因**（`create-vue` 在没有任何 feature flag 时会转成交互式提问，所以"JavaScript + 无附加项"改用 `create-vite --template vue`）；React 的 linter **显式**写清 `--eslint` / `--no-eslint`（默认是 Oxlint，不写会让用户以为选的 ESLint 没生效）。新增一个 `--network` 显式点名才跑的端到端场景，真调 `npm create` 验证三条官方路径。**拆完之后向导长过了一屏**（1130px > 821px 的窗口，导致「前后端项目」的「创建」按钮落在视口外、根本点不到）—— 已改成「头尾固定、内容区滚动」，并新增 `wizard-layout` 场景永久盯住这条不变量（四种项目类型各量一次：不超视口 + 按钮点得到，并留图人工复核）—— 这一条**功能断言当时是全绿的**，是拍图量数字才发现的。实施记录见 technical-design §44 |

## 1. 定位与目标

Windows 桌面端 **「项目管理 + 项目脚手架」一体化工具**：既能管理项目的任务、工单与文档，又能在新建项目时**一键把代码骨架、依赖、环境全部铺好**，并把生成的代码目录纳管为 PM 项目。

**核心目标**

1. 个人主力可用，功能完整、数据可迁移、长期可靠。
2. 新建项目从「填表」升级为「填表 + 环境就绪 + 代码就绪 + 任务就绪」。
3. 架构上为将来多人协作预留空间，但不为尚未需要的复杂度买单。

**明确不做的事**：见第 6 节。

## 4. 架构设计

### 4.1 三层结构

```
┌──────────────── Vue3 渲染进程 ────────────────┐
│  Pinia 状态 / 路由 / Naive UI                 │
│            ↓ HTTP（永远只走 HTTP）             │
│  内嵌 Fastify 服务（127.0.0.1 + 动态端口）      │
│            ↓                                  │
│  SQLite（位于当前工作区内）                     │
└──────────────────────────────────────────────┘
```

- 前端**永不直连数据库**，所有业务逻辑集中在 API 层。这是「真正预留远程」的前提。
- 内嵌服务监听**动态空闲端口**，避免与用户机器上其他程序冲突。

### 4.2 本地 / 远程双模式

- **第一版只做本地模式**，远程模式不实现。
- 但架构上从第一天预留：
  - 数据库所有表带 `user_id` / `owner_id`，本地固定为 `local-user`；
  - API 层统一鉴权中间件，本地放行、远程启用 JWT；
  - 前端 API baseURL 可配置，远程模式仅换地址，前端与 API 层代码零改动。
- **不做**离线编辑与双向冲突同步。远程模式将来为纯在线。

### 4.3 工作区与数据归属

- **每个工作区 = 一个自带数据库的便携包**，目录结构（**0.1.2 起**）：

```
<工作区>/                     ← 打开只看到项目
├── 我的项目A/                ← 一个项目一个文件夹（代码就在这一层）
│   ├── attachments/          ← 该项目的附件
│   └── logs/                 ← 该项目的作业输出与相关错误
└── 我的项目B/
```

- **管理数据不在工作区里**：项目登记、任务、看板、标签等存在 `<userData>/data/workspace.db`，
  与工作区目录平级。分开的理由是用户打开工作区目录时**只应看到自己的项目**，
  而不是一个躺在项目旁边的数据库文件。（0.1.1 及更早，数据库在工作区内部。）

> **⚠️ 迁移注意**：数据库移出工作区后，"便携包"是**两件东西** ——
> 工作区目录（项目）与 `data/workspace.db`（登记与任务）。只拷其一会丢数据。
> 想做"一键迁移"需要另做一个导出功能（见 §13.1 之后的待办）。

- **AppData 只保存很小的全局配置**：工作区清单（路径、名称、最后打开时间）、当前激活工作区、全局偏好（主题、默认根目录）。该配置丢失可重建。
- **支持多个工作区并存、随时切换**。切换工作区 = 切换数据库连接 + 切换代码根目录，各工作区数据天然隔离。

**测试环境与正式环境（0.1.9 起）**

开发调试用的数据与正式数据**必须是两套**，否则「一边开发一边试功能，测试项目就灌进了正式数据里」。规则很简单 —— 整个 `userData` 根目录按环境切换：

| 场景 | 环境 | 数据目录 |
|---|---|---|
| **打包后的应用**（安装版 / 免安装版，`app.isPackaged = true`） | 正式 | `%APPDATA%\@pm-studio\desktop` |
| **开发运行**（`dev` / `preview`，未打包） | 测试 | `%APPDATA%\@pm-studio\desktop-test` |
| 显式 `--user-data-dir=...` | 自定义 | 参数指定（测试脚本的沙箱，优先级最高） |

- 「**打包时切到正式环境**」不需要任何手工动作：打包产物天然满足 `isPackaged`，自动落在正式目录；反过来开发版**永远碰不到正式数据**（除非显式设 `PM_STUDIO_ENV=production`）。
- 数据库、工作区目录、config.json、日志**都在这两个根目录下面**，所以整套状态一起隔离，不存在"库分开了但工作区还混着"的半吊子状态。
- **界面上必须能看出在哪个环境**：窗口标题（非正式环境带 `（测试环境）` 后缀）、侧栏版本号旁的环境标签（悬停显示实际数据目录）、托盘提示。数据分了两套之后，最大的风险是"不知道眼前这份是哪套"。

### 4.4 窗口与进程生命周期（托盘驻留）

- 点击窗口关闭按钮 → **默认最小化到系统托盘**，不退出应用。
- **完全退出**：右键点击右下角托盘图标 → 菜单「退出」。
- 单实例锁：重复启动时激活已有窗口，不新建进程。
- 托盘图标右键菜单：显示主窗口 / 打开工作区目录 / 退出。
- 退出时若仍有作业在运行（如 `pnpm install`）→ **二次确认**，用户可选择等待完成或强制终止并清理。
- （后续可选）开机自启开关。

## 5. 功能需求

### 5.1 工作区管理

- 创建工作区：由用户选择保存位置（系统给出建议路径，可修改）。
- 工作区列表：切换、重命名、在资源管理器中打开、删除（二次确认，默认不删磁盘数据）。
- **迁移工作区**：修改工作区路径时，把旧位置的全部内容搬运到新位置。

**迁移流程（安全版，必须严格按序）**

1. **预检**：目标路径可写、磁盘剩余空间 ≥ 源目录 2 倍、无文件被占用（VS Code / dev server 常锁文件）、路径长度检查。
2. 对 SQLite 执行 **WAL checkpoint**，**关闭数据库连接**（否则 `.db` / `-wal` / `-shm` 复制必然出错）。
3. **复制**整个工作区到新路径（**不删除源**）。
4. **校验**：文件数量 + 总大小 + 关键文件哈希比对。
5. 校验通过 → 改写新库内的所有绝对路径（项目路径、附件引用）。
6. 切换当前工作区到新路径，重新打开数据库。
7. 确认可用后，**才删除旧目录**。
8. 全程进度 + 日志 + 可取消；中途失败保留原目录，**保证任何时刻至少存在一份完整数据**。

**同名冲突**：目标目录已存在同名项目或文件夹 → **自动重命名并保留双方**，后缀格式 `xxx_copy`（再冲突则 `xxx_copy2`），迁移结束后输出完整清单报告。

### 5.2 项目与任务（地基）

- **项目**：名称、描述、颜色、归属工作区、绑定代码目录（可为空）、归档、回收站。
- **任务**：标题、描述（Markdown）、负责人、起止日期、状态、**优先级**、**标签**、父任务（**支持多层子任务**）。
- **任务依赖关系**：前置 / 后置任务，为 M6 甘特图的依赖线与关键路径打基础。
- **操作**：拖拽排序与改状态、批量编辑、复制、归档、回收站还原。
- **活动记录**：不做评论功能；系统自动记录关键变更的最小活动日志。

#### 5.2.2 项目的启动与停止（2026-09-28 用户提出，v2.16 已实现）

- **只有前端、后端、前后端项目有启动 / 停止按钮**（用户明确要求）—— 纯管理项目没有代码，
  连"能不能启动"都是 false，界面上就不会出现按钮。
- **启动** = 起这个项目的开发服务器（前后端项目起来是**两个进程**，各自有端口）：
  Vite `<pm> run dev`、NestJS `<pm> run start:dev`、Django `manage.py runserver <port>`、
  FastAPI `-m uvicorn app.main:app --reload --port <port>`；端口从生成出来的
  `vite.config.*` / `.env` 里读，读不到用各栈默认值（5173 / 3000 / 8000）。
- **停止** = 结束**整棵进程树**（`taskkill /PID <pid> /T /F`）。只杀外层会留下真正在监听端口的
  孙进程 —— 端口还占着，用户点过"停止"却起不来第二次。
- **依赖没装好就别启动**：没有 `node_modules` / `.venv` 时会被挡下并说明"先跑一次安装依赖"，
  而不是显示成"已启动"。
- **按钮在哪**：项目卡片操作区里那一格（原先是个禁用的假占位"等作业系统（M4）接入后可用"，
  v2.16 已换成真的按钮）；纯管理项目**没有这一格**（不是"有但禁用"）。
- **要让用户看见程序在跑**：运行中时卡片上多一个「在浏览器里打开」入口，点开就能看到页面；
  停止后该入口立刻收起。
- **地址不许自己拼**（2026-09-29 实测踩到）：开发服务器绑哪个回环是它自己决定的 ——
  Vite 默认绑 `localhost`（可能解析成 `::1`），我们拼 `127.0.0.1` 就会让用户点开是"无法连接"，
  现象是"没启动"。所以地址**从进程输出里读**（Vite 自己会打印 `Local: http://localhost:5173/`，
  顺便解决"端口被自动换掉"），并且**探测到真的能连上之后**才给"打开"入口；
  没通之前显示"服务已启动，但地址还没通（第一次要预构建依赖）"。
- **点「运行中」能打开运行面板**（操作区里也有一个「运行详情」按钮）：里面是每个目标的状态、命令、
  真实地址、是否连通与**启动输出**，能就地停止，并且**打开时自动跟随输出**（像终端一样往下走）。
- **端口会真的写进生成出来的配置**：官方脚手架（`create-vue` / `create-vite` / `nest new`）
  自己不写端口，所以官方生成完之后由我们补上（`vite.config.*` 的 `server.port`、
  NestJS 的 `app.listen(...)`）；认不出技术栈就**什么都不改并说明**。
- **缺依赖时卡片上出现「装依赖」**：点了在运行面板里跑安装作业，进度与安装输出都在面板里，
  装完入口自己收起（依赖齐了就不显示这一格）。提示里说"先跑一次安装依赖"时，**界面上真的有地方能跑**。
- **输出要能看**：启动输出（含端口号）边跑边收，界面上能看到"到底跑起来没有"。
- **状态只在内存里**：应用退出时全部停掉；应用重启后不会留下"显示运行中、其实没进程"的假状态。
- **不做**：自动重启、热重载开关、把服务器日志写进项目里、部署/发布（那是另一件事）。

#### 5.2.1 项目间关系链（**纯展示**，2026-09-26 用户提出）

**唯一的跨项目的东西**：项目与项目之间可以标一条关系（例如「前端项目 → 调用 → 后端项目」），
在管理系统里**只是显示这层关系**；两个项目的数据**互不可见、互不影响**。

- 定这条的理由（用户原话）：「项目之间都是单独存在的，在管理系统中只有项目与项目的关系链，
  比如一个前端项目和一个后端项目，两者之间**在项目内**存在前端访问后端的关系，
  但在项目管理系统中**无任何其他关联**」。
- 因此这条关系**不允许**带来任何联动：不共享任务/标签/状态/文档，不做跨项目的进度汇总，
  不做"改了 A 就影响 B"的规则。它和"工单↔任务"一样，属于 §11 决策 #28 里的"只做展示"。
- **状态：已实现（2026-09-28，v2.15）**。四个待定问题定成：**有向**（前端 → 调用 → 后端）、
  关系名称**自由填**（40 字上限，因为用户给的例子「调用」「同属一个系统」说明枚举立刻不够用）、
  显示在**项目卡片**（关系名小标记）与**总览**（能增能删的「关系链」面板）。
- 落地时从**数据形状**上就把"不联动"焊死：`project_relations` 只有两个端点、一句说明与时间戳，
  **没有** kind 枚举 / 权重 / 联动开关；也**不做环检测**（关系只用来画线，做了环检测
  用户反而没法标"A 调用 B、B 回调 A"）。服务端只校验：两端项目存在且未删除、不能连自己、
  同一对端点同名不重复、名称与备注有长度上限。
- 两个方向都查得到（后端项目那一页也要能看到"谁在调我"）；项目**软删除时关系保留**（恢复后还在）、
  **物理删除时跟着清掉**并留一笔活动记录。实施记录见 technical-design §48。
### 5.3 工单流（需求 / 缺陷）

- 工单类型：需求、缺陷，且类型可扩展（**项目级**，见 §13.2）。
- **状态可自由增删、重命名、排序、配色**。
- 每个项目一套独立的状态配置，通过状态模板一键套用。
- **默认的六态流程**（2026-10-02 用户定，四个技术栈共用一套）：
  **待完成 → 正在修改 → 待审查 → 审查中 → 回退修改 → 已完成**。
  分类（`category`）仍然只有三种：`todo` / `doing` / `done`，**只有「已完成」是 `done`** ——
  所有"算不算做完"的判断都看分类，所以"今日待办不含已完成""工作日志统计完成数"这类逻辑
  不因为状态变多而改。用户仍然可以改名、增删、调顺序。
- **工单状态与任务状态共用同一套**（用户 2026-09-26 定）；两者在语义上的区别见下。
- 工单可与任务相互关联（**同项目内**，且只做展示与跳转，不改任务本身）。

> **工单状态表示什么**：它回答「**这张工单（需求 / 缺陷）处理到哪一步了**」。
> 与任务状态共用同一张 `workflow_statuses`（项目级、可增删改名列排序配色）之后，
> 同一组状态名会同时出现在任务和工单上 —— 这是"共用"的真实代价：
> 如果给项目配了"已确认 / 待验证 / 已关闭"这类工单专用状态，它们也会出现在任务的换状态下拉里。
> 想彻底分开（给状态表加 `scope` 列）随时可做，但要走一版迁移，所以先共用。

### 5.4 文档与知识库

- **Markdown 编辑器**，带实时预览、代码块、表格、图片粘贴。
- 文档树 / 目录组织：支持项目内文档与独立知识库空间。
- **附件**：实体文件存放于项目文件夹内的 `attachments/`（0.1.2 起一个项目一个文件夹），
  数据库存元数据（远程模式下可替换为对象存储）。**附件的出现时机**：M3 文档功能上线之后
  （在文档里粘贴图片、上传文件）；在此之前这个目录一直是空的。
- **历史版本**：指**文档正文的快照** —— 每次保存把上一版内容留一份，可查看、可回滚，
  防止误删误改（与"任务/工单的最小活动日志"是两回事，后者只记关键变更、不存正文）。
  保留策略待定（建议保留最近 20 版）。
- **备份含附件**（用户 2026-09-26 定）：现在的"立即备份"只导出一份数据库文件
  （`<userData>/backups/workspace-<时间>.db`，走 SQLite 的 backup API）；
  加入附件后备份要变成"数据库 + 各项目 `attachments/`"的整包，
  并且需要一并考虑**恢复**怎么做（现在只有"打开备份目录"，靠用户手动覆盖数据库）。

#### 5.4.1 独立知识库是干什么的（定位初稿，2026-09-26）

**一句话**：装**不属于任何项目的那部分知识** —— 跨项目复用的方法、命令、模板、复盘与学习笔记。
它的价值不在"能写文档"（项目内文档也能写），而在**以后新建项目、写任务时能直接拿来用**。

第一版应该收得住的东西（推荐先做的打 ✅）：

| 用途 | 例子 | 先做 |
|---|---|---|
| **跨项目复用的操作手册** | 部署步骤、环境配置备忘、内网/VPN、镜像源怎么配 | ✅ |
| **项目启动清单 / 规范模板** | 上线检查清单、需求评审清单、复盘模板、周报模板 | ✅（**M4 新建项目向导可以直接引用**，这是它和脚手架模块的接口） |
| **代码片段与踩坑记录** | "SQLite FTS5 中文分词要用 trigram""Electron 打包的三个坑" | ✅ |
| **学习笔记 / 专题积累** | 读书笔记、技术专题、面试题 | ✅ |
| **临时收件箱** | 先记一句话，之后再整理进某个项目 | ⏳ 二期（要配合"移动到项目"） |
| **资源台账** | 服务器、域名、端口、部署目标 | ⏳（**不要放密码/密钥**） |

**不做**（避免变成大杂烩）：跨项目的任务/工单汇总（那是「我的待办」的活）、
多人协作与权限、评论、Notion 式的块级数据库。就是一棵 Markdown 文档树。

**明确不加密**：知识库正文与附件都是明文（备份也是明文包），所以**不要往里放密码、密钥、
身份证这类东西** —— 这条要写在界面上，不能只写在文档里。

**两个待定细节**（做之前要定）：

1. **附件落哪** —— ✅ **已定（2026-09-26）**：**附件存自己项目里**（用户原话：「附件存在自己的项目中，
   比如前端的图片是保存在他项目内的」）。这与既有结构一致：项目文件夹在创建时就建好了
   `attachments/` 与 `logs/` 两个子目录（`services/project-folders.ts`），附件落在
   `<工作区>/<项目文件夹>/attachments/`。
   由此推论：**知识库不属于任何项目，所以它需要自己的一处位置** —— 建议
   `<userData>/knowledge/attachments/`（**不放工作区**，因为"打开工作区只应看到自己的项目"是 §4.3 的硬规则）。
   于是"备份整包"要收三处：`<userData>/data/workspace.db` + 各项目的 `attachments/` + 知识库目录。
2. **标签怎么办**：项目标签要改成项目级（§13.2），知识库不属于项目 → 用不了项目标签。
   要么知识库第一版不做标签，要么做"知识库自己的标签"（属于空间而不是项目）。建议先不做。

**两个必须提前知道的坑**：

- **`attachments/` 在代码目录里**（一个项目一个文件夹，代码就在这一层），所以文件和 `src/`、
  `package.json` 是邻居：`git status` 会看到它们（M6 的 Git 集成、或用户自己敲 git 时），
  图片动辄几十 MB，**一旦提交进仓库就很难收拾**。建议新建项目时**往 `.gitignore` 追加**
  `attachments/` 与 `logs/`（追加，不覆盖脚手架已生成的内容）——这条要在 M3 落附件时一起定。
- **文件被手动删掉**：用户可能在资源管理器里删了 `attachments/` 里的图片，而数据库里还记着它。
  界面上要能看出"这个附件缺失"（而不是打开时白屏或报错）。

**和项目内文档的关系**：同一套引擎（Markdown 编辑器 / 树 / 附件 / 历史版本），**只差归属**。
所以"保留知识库"几乎不增加实现成本；真正要额外做的是**「复制到项目 / 从项目移到知识库」**这个动作。

### 5.5 视图与搜索

> **2026-09-24 结构调整**：原先规划的「看板 Kanban（按状态分列）」被用户否掉 ——
> 「不要分四个大类，任务状态之间在任务卡片中用标签展示」。看板与列表两页因此合并成
> 一个「工作台」（任务增删改查的唯一主战场），另外新增一个「总览」页，
> 关系表达集中到总览里的**六边形关系数据图**上。下面表格是调整后的口径。

> **2026-09-30 再调整（0.2.1）**：用户要求「给工作台和我的待办进行完全重构」：
> **工作台 → 工作大纲**（从上到下的树，父子之间画正交圆角连线；取代"分层空间"），
> **我的待办 → 今日待办**（只显示今天要做的事 + 当日工作时间 + 生成工作日志）。

| 视图 | 里程碑 | 说明 |
|---|---|---|

| **今日待办** | M2 → 0.2.1 重构 | **只显示当前项目**（用户 2026-09-30 定：「今日待办只展示当前项目的任务内容」；侧栏这一项因此需要先选项目）。**两种口径可切换**（用户 2026-10-02：「这里我需要展示当前项目的所有任务」）：**今日待办**（默认）= 今天到期 + 逾期未完成 / 今天开始 / 今天动过 / 手动标记 四组做筛选，一条任务可同时属于多组，所以"全部"是**去重后的并集**，每张卡片直接标出它"为什么在今天"（逾期用红字提醒，自己筛某一组时只显示那一枚标签），**已完成的不进列表**；**全部任务** = 当前项目的**全部**任务（含已完成，副标题写明"共 N 条 / 含已完成 M 条"），此口径下收起四个来源筛选。**每张卡片标出所属项目**；卡片与工作大纲**同款同功能**；点卡片开详情。手动标记是卡片上一个**星标图标按钮**，悬停提示「添加今日待办」，标记按**日期键**存 → 第二天自然失效（不需要任何定时清理） |
| **当日工作时间（打卡）** | 0.2.1 新增 | 口径是**应用开着的时间**：「每天第一次打开软件开始计时，到最后一次关闭结束」，一天里多次开关算**合计**；`HH:MM:SS` 跟着时间跳（渲染层本地推进，不每秒问服务端）；应用被强杀（断电、结束进程）时那段只计到**最后一次心跳**为止——宁可少算几十秒，不能凭空多算几小时；跨午夜的会话按天算交叠、不拆行 |
| **生成工作日志** | 0.2.1 新增 | 在「今日待办」里一键生成**当天的 Word 文档**（真 `.docx`）：**四段结构**（今日概要 / 工作时段 / 分项目进展 / 说明），不是"把当天操作贴成一个列表"；生成**前**先显示文档里会有多少内容，生成**后**显示**真实路径**并可打开文档 / 打开所在文件夹；同名文件覆盖前**如实告知**（用户可能已在 Word 里改过）；文件名以当日日期开头；保存位置在**设置 → 工作日志**里可改（默认 `<文档>\项目管理系统\工作日志`） |
| **全局搜索** | M2 ✅ | 任务与工单的全文检索，跨项目，结果标出所属项目。**中文片段可搜**：3 字以上走全文索引（trigram），少于 3 字自动回落模糊匹配，界面如实说明走的是哪种；结果卡片与工作大纲同款 |
| **功能介绍** | M2 ✅ | 设置页版本号下面进入：先看**版本列表**，点某一版看它多了什么、修了什么（数据在 `data/whats-new.ts`，每次发版在最前面加一条） |
| 跨项目聚合 | M2 ✅ | 由「今日待办」承担 |
| 甘特图 / 时间线 | M6 | 依赖线、里程碑、关键路径 |
| 拖拽（改状态 / 改归属 / 排序 / 大纲换层级） | 第二期 | 第一期先把「看与改」做扎实，拖拽单独一期做 |

**为什么状态不做成分列**：分列的前提是"状态数量少且稳定"，而本项目的状态是
每个项目自定义的工作流（可以有 6~8 个），分列会把一屏切成很多窄条，
子任务还会因为状态不同而被拆到不同列里 —— 父子关系随之散掉。
把状态降级成卡片上的标签之后，同一棵子树始终待在一起。

**工作大纲里"整棵树一起看"取代了"点进去看下一层"**（2026-09-30）：原来的分层空间
一次只能看一层，想确认"这件事挂在哪个父任务下"要靠回忆面包屑；树把层级、兄弟顺序
和整棵子树的规模一次摆出来。代价是节点比卡片小、宽树要横向滚动，所以节点上的操作
（加子任务 / 改名 / 删除）做成了悬停出现的小按钮；打开详情则直接点卡片本体。

### 5.5.1 设置页（0.2.0 / M2 新增）

> **2026-09-25 新增需求**：用户要求「添加一个设置页」。
> 这些偏好本来就在 `<userData>/config.json` 里，只是一直没有界面 ——
> 想改日志级别、换编辑器、看数据存在哪，都只能去翻配置文件。

| 分区 | 内容 | 生效时机 |
|---|---|---|
| **外观** | 主题（亮色 / 暗色 / 跟随系统） | 立即生效 |
| **默认编辑器** | **自动识别这台电脑装了哪些编辑器**，从识别到的里面选 | 立即生效 |
| **日志与诊断** | 记录级别、保留天数、单个文件上限（MB）、保留份数、是否隐藏用户名 | 级别**立即生效**；其余下次启动生效 |
| **备份** | **立即备份一次**（可用）+ 定时自动备份开关/间隔/保留份数（只存配置，功能未实现，界面如实标注） | 见说明 |
| **GitHub 绑定** | **预留接口**：显示绑定状态（未绑定 / 已绑定到谁）+ 「绑定 GitHub」入口。**OAuth 流程尚未实现**，点了会明确告知，并说明将来怎么做 | 见说明 |
| **数据与环境** | 当前环境（正式 / 测试 / 自定义）、数据目录（可打开）、**工作区目录（可更改）**、版本 | 见说明 |
| **功能介绍** | 版本号下面一个入口 → **版本列表** → 点某一版看它"多了什么 / 修了什么" | 静态页面 |

**「功能介绍」是一页，不是弹窗**（2026-09-25 补充，用户先说「设置里加个功能介绍」，
看到弹窗版本后改成「这里单独做一个页面」）：版本会越攒越多，弹窗里放不下、
也没法把某一版的内容收藏或转发。现在是**列表 + 详情**两态（同一个视图，
路由 `/whats-new` 与 `/whats-new/:version`），数据在 `data/whats-new.ts`：
**以后每次发版在最前面加一条**即可。版本行与上面的分区之间用一条分隔线隔开，
它不属于任何分区（是"关于"类信息）。

> **发版时要改两处**：界面这一份（`data/whats-new.ts`）和给人看的那一份
> （`docs/release-notes.md`，含安装包与升级说明）。发版清单在后者末尾。

**GitHub 绑定是预留接口**（2026-09-25 补充，用户原话「设置里预留绑定 github 的接口」）：
Git 集成整体排在 **M6**，所以这一版**不做 OAuth**，但把三件事先定下来，
以后动的是实现、不是契约：

1. **接口形状**：主进程提供 `github:status` / `github:connect` / `github:disconnect`，
   状态对象固定为 `connected / login / hasToken / connectedAt`（外加 `available`
   告诉界面"这一版能不能绑"）。界面按 `available` 判断，不写死。
2. **令牌绝不进配置文件**：`config.json` 是明文 JSON，会被备份、会被打进诊断包、
   也可能被随手转发。配置里只放"绑没绑、绑的是谁"，令牌将来用 Electron `safeStorage`
   加密后单独存 `<userData>/github.credential`，**也不经过渲染层**。
3. **不假装成功**：点击「绑定 GitHub」会明确弹出"尚未实现（排在 M6）"，
   而不是转个圈、或者点了没反应 —— 后者会让人以为已经绑好了。
   「解除绑定」倒是现在就是完整的（清本地状态 + 删令牌文件），因为不依赖 OAuth。

实现时走 **OAuth Device Flow**（浏览器里输一次验证码，桌面应用不需要内嵌 client secret，
也不用起本地回调端口），作用域按需最小化；主进程自带 `fetch`，**不需要引入新依赖**。

**设置页里只有主题，密度与侧边栏不重复出现**（2026-09-25 补充，用户原话「这两个不要」）：
界面密度与侧边栏折叠在顶部工具条 / 侧栏把手上已经有开关，同一个设置出现在两处，
只会让人怀疑"我是不是改错了地方"。

**日志页的排版**（2026-09-25 补充，用户原话「当数据没有的时候我也希望他在这里」）：
分页栏（上一页 / 下一页）**始终贴在内容区底部**，不管有没有数据。
原来有数据时列表撑开高度、分页栏自然落底；没有数据时空态撑不开，分页栏就浮到了工具栏下面，
看着像排版坏了。

**日志页要能区分"历史噪音"和"现在的错误"**（2026-09-25 补充，起因是用户问「日志问题有解决吗」）：

查下来正式库里 12 条 error 全是**两三天前旧版本留下的**（8 条浏览器无害告警 +
4 条来自早就删掉的旧看板/列表页面的异常），当前版本实际是零错误。
但日志只增不减，历史红字会一直躺在那里 —— 用户每次打开都要重新怀疑"是不是又坏了"。
所以：

- **浏览器自身的无害告警降级显示**：显示成灰色「提示」而不是红色 error，整行压暗，
  页面顶部说明"这不是应用错误、当前版本已不再上报"。判断规则与"不再上报"共用一份。
- **新增「清空」按钮**（带确认）：把历史清掉、从干净状态重新看。清空动作本身会留一条记录，
  免得"日志怎么突然空了"变成新谜团。

> **2026-10-02 起这一节作废**：用户要求「所有任务的进度条都取消」，进度这个字段
> 从界面上与 DTO 里整体下线，改由**六态状态**表达"做到哪一步"（见 §5.2 的状态说明与
> technical-design §51）。下面这段保留下来，是因为它记录的"边输入边保存导致焦点被抢"的
> 教训对将来任何输入控件都成立。

**（以下为 2026-09-25 的历史记录）进度是进度条，不是数字输入框**（用户原话「当我输入时就会失去焦点，
这里改成进度条，点一次+值就变大 10」）：

- 交互：**点进度条任意位置**跳到那里（按 5 对齐）、**按住拖动**连续调整（松手才提交）、
  「−10」「+10」按钮一次 10、键盘方向键 ±10、Home/End 到 0/100。
  **拖动过程中不发请求**，只有松手才提交一次。
- 「失去焦点」的根因不是输入框本身：它绑了 `:disabled="saving"`，而每敲一个字符都会
  发一次保存请求、保存期间 `saving=true` —— 于是"敲数字 → 请求发出 → 输入框被禁用
  → 重新渲染 → 焦点掉了"。换成进度条之后**不存在需要保持焦点的输入态**，
  这个问题从结构上消失。
- 顺带修掉一个相关的老毛病：详情里每改一个字段都会**整块重载**任务，而重载会把
  标题/描述草稿按服务端值重置 —— 在描述里写了一半、顺手改一下优先级，写的内容就没了。
  现在改成**用服务端返回的那条就地合并**，不重载、不动草稿。

**设置项用名词，不用问句**（2026-09-25 补充，用户原话「改成默认编辑器」）：
编辑器这一项原来叫「用哪个编辑器打开项目」，是一句问句，而其它分区里的设置项都是名词
（主题 / 记录级别 / 日志保留天数…）。现在分区名是「编辑器」（话题），
设置项名是「默认编辑器」（这一项本身），和其它分区保持一致。

**编辑器改成"识别本机"**（2026-09-25 补充，用户原话「改为选择默认编辑器，可以执行识别
电脑上存在什么编辑器」）：原来是固定列出 8 个命令（webstorm / idea / subl…），
用户面对一堆自己没装的名字无从下手。现在**先探测再让人挑**：复用"用编辑器打开"那条
路径上的解析逻辑（PATH → 反推 exe → 常见安装位置），只列真正解析得到的；
当前配置的那个如果没检测到（换了机器），仍然保留并标注「未检测到」，
否则下拉会显示成空白，看起来像设置丢了。

**「界面密度」已下线**（2026-09-25，用户反馈「删除系统的密度切换功能，这个看着很鸡肋」）：

上一轮刚把它做大（紧凑 34px / 13px，舒适 42px / 14.5px，差得看得见），
但用户看下来认为**这个开关本身没价值** —— 一屏里能多放一张卡并不值得多一个全局状态，
于是连同样式一起删掉。现在固定 **`comfortable`**：控件 42px、正文 14px。
存储里的旧 `density` 字段保留但不再读，免得老配置升级时报错。
（原先那两条量高度的 e2e 断言随之删除，改成量"控件确实是 42px"。）

**工作区目录可以改**（2026-09-25 补充，用户原话「这里需要可以修改工作区目录」）：

- 点「更改目录」→ 系统目录选择框 → 如果当前有项目，再问一句**「要把现有项目一起搬过去吗？」**
  （一起搬 = 把项目文件夹移动到新目录；只切换 = 新目录先空着，旧文件夹留在原地）。
- 搬家用的是重命名，同盘瞬间完成；**跨盘会失败，此时如实报出并让你手动拷** ——
  不做"复制 + 删除"那种两步操作（那才是真会丢数据的操作，留给 M5 的工作区迁移）。
- 目标位置已有同名文件夹时**跳过并告警，绝不覆盖**。
- 切换后应用会提示**重启一次**：内嵌服务仍拿着启动时的工作区路径（新建项目建文件夹、
  导出诊断包都用它），重启后所有组件才读同一份新配置。
- 界面上显示的路径（本页 + 侧栏底部）**立即更新**，不用等重启。

**「保留份数」是什么意思**（用户反馈"我没有理解"）：备份文件堆着不动会一直占地方。
留够 N 份之后，再备份就自动删掉最旧的那一份 —— 填 10 就是"最近 10 次备份留着，
更早的自动删掉"。这句解释现在直接写在界面上，而不是只留一个数字输入框。

两条写进需求的硬约束：

1. **"立即生效"与"下次启动生效"必须在界面上说清楚**。两者混在一起显示，用户会以为设置没保存
   （明明存了、却还是老行为）。日志级别之所以能立即生效，是因为主进程拿到了 `setMinLevel`；
   文件轮转参数与脱敏要重建日志写入器，只能下次启动。
2. **没实现的功能要如实标注，不能只放一个开关**。"自动备份"目前只有配置项、没有后台任务，
   勾上它并不会真的备份 —— 界面直接写明，并指路手动复制数据目录。
   一个写着"自动备份：开"却没有备份的界面，比没有这个开关危险得多。

另外，设置页是**第一个显示"当前环境 + 数据目录"的界面**（见 §4.3 的环境隔离）：
用户在设置里就能看清自己正在动哪一份数据。

### 5.6 项目脚手架

**模板来源策略（优先级从高到低）**

1. **有官方脚手架 → 调用官方**：`create-vue`、`npm create vite`、`nest new`、`django-admin startproject`（全部以非交互参数程序化调用）。
2. **无官方脚手架 → 使用内置固定模板**：**FastAPI 首当其冲**（官方无脚手架），以及官方参数无法覆盖的定制骨架。
3. **官方调用失败（网络异常 / 版本变动）→ 自动回退内置模板**，并在日志中明确告知实际走了哪条路径。

> **内置模板的内容从哪来（2026-09-26 用户：「M4 的生成模板可以在网上找相关的脚手架」）**：
> **开发期从网上/官方模板仓库取现成产物，固化进应用；运行期不下载模板。**
> 具体取自哪些仓库、为什么不能运行时下载（回退的意义就是离线可用）、以及
> 许可证与"模板里不许带可执行脚本"这两条约束，写在技术设计 §5.5 的「模板内容从哪来」。
>
> **落地现状（2026-09-28）**：
> - **Vue 3（`npm create vue@latest`）、React（`npm create vite@latest`）、NestJS（`npx @nestjs/cli new`）
>   走官方脚手架**：先跑 `--help` 探测参数（官方参数随版本变，硬编码迟早崩），认得就调官方；
>   官方走不通（断网 / 参数被改）→ **回退内置骨架**并在日志里说明"这是最小骨架、比官方少什么"。
> - **Django 也走官方**（`django-admin startproject`），但它多一段**前置**：官方工具不自带，
>   先在项目自己的 `.venv` 里装 Django（这一步要联网，装的还是用户在向导里选的那个版本），
>   装完再把 `startproject` 跑在项目内；前置失败**同样回退内置骨架** ——
>   不能因为"装不上 Django"就让用户连一个能跑的项目都拿不到。
> - **FastAPI 用内置模板**（官方没有脚手架）。
> - 五种技术栈因此**都能离线起步**。实施记录见技术设计 §40、§42、§47。

**第一版支持的技术栈**

- 前端：**Vue 3**（TypeScript / JavaScript）、**React**（TypeScript / JavaScript）
- 后端：**NestJS**、**Python（FastAPI / Django）**
- 每个栈都能再选**框架版本**与**附加项**（Vue：Router / Pinia / ESLint / Prettier / Vitest / JSX；React：ESLint；NestJS：严格模式）
- 暂不支持（第二版）：Java / Spring Boot、Svelte 等

**组合方式**：支持一个项目同时生成前后端，落盘为 `frontend/` + `backend/` 两个子目录。

**包管理器**：自动检测机器上已安装者（pnpm / npm / yarn）并采用，向导中可手动改。

**依赖安装**：生成后自动执行 → Node 侧 `pnpm install` / `npm install`；Python 侧**自动创建 venv 并在其中 `pip install`**。全程带进度、实时日志与取消按钮；允许在向导中勾选「跳过安装」。

### 5.7 环境检测与自动配置

**检测（首次强制，之后走缓存）**

- 新建项目向导**第一步**强制检测，结果写入数据库缓存，后续新建时自动跳过。
  > **现状（2026-09-26，M4 第一步已落地）**：检测本身已经实现并接到**设置页**上
  > （「开发环境」分区：8 个工具一行一个，路径 + 版本 + 用途，可点「重新检测环境」）。
  > **缓存放在 AppData**（`<userData>/environment.json`）而不是数据库 ——
  > 它描述的是"这台机器"，不是项目数据（§13.1），而且换工作区后同一个结果继续有效。
  > **向导第一步的"强制检测"要等向导做出来**（M4 后面几步）。
- **必须提供「重新检测环境」按钮**：用户后来安装了新工具或切换了 Node 版本时用于刷新。一次性检测做死会埋坑，因此不允许永久跳过。
  > **已实现**，并且额外给了一条提示：检测时记下 PATH 指纹，若用户在这次启动之后改过环境变量，
  > 界面上会说明"**需要重启本应用**才能生效"（Windows 下已运行的进程读不到新 PATH）。
- 检测对象：`node` / `npm` / `pnpm` / `yarn` / `python` / `pip` / `git` / `venv` —— 是否存在、版本号、是否位于 PATH。
  > **已实现 8 项**。`venv` 是**能力探测**（`python -m venv --help`），界面上显示「可用 / 不可用」；
  > 真正的格式差异见技术设计 §38。另外"取版本号失败"会把原因显示出来，**不会显示一个编出来的版本号**。
- 检测不通过 → 阻止进入下一步，并给出明确的修复指引与可复制的命令。
  > **部分实现**：设置页会明确列出"缺少必需工具：xxx"；**"阻止进入下一步 + 可复制命令"要等向导**。

**自动配置（用户已确认，需带安全约束）**

> **现状：尚未实现**（按用户点选的顺序，改机器的这一步放在 M4 最后做；
> 默认值已定：**三项默认勾选上**，见决策记录 #39）。下面是实施时必须守住的约束。

| 项 | 行为 | 安全约束 |
|---|---|---|
| 用户级 PATH | **只追加缺失项，绝不覆盖** | 改前将原值**备份进数据库**，提供**一键回滚** |
| npm 镜像源 | 写入 `.npmrc`（如 npmmirror） | 改前备份，可回滚 |
| pip 镜像源 | 写入 `pip.ini` | 改前备份，可回滚 |

- 三项**各自独立可勾选**，也可逐项回滚。
- **不修改系统级环境变量**（需管理员权限，影响面过大）。

### 5.12 日志与诊断（v1.1 新增）

**目标**：应用内直接查看报错日志，出问题时能当场定位到现场，而不是去翻文件、开命令行猜。

**日志来源分为四个分区**

| 来源 | 内容 |
|---|---|
| `main` | Electron 主进程：启动、托盘、窗口生命周期、未捕获异常 |
| `api` | Fastify 请求与错误：错误码、堆栈、请求耗时 |
| `job` | 作业子进程输出：脚手架生成、依赖安装、工作区迁移 |
| `renderer` | 前端错误：Vue `errorHandler`、`window.onerror`、`unhandledrejection`、白屏 |

**日志级别**：`error` / `warn` / `info` / `debug`。默认 `info`，设置里可临时切到 `debug` 深度排查。

**查看能力**

- 日志列表：按**级别、来源、时间范围、关键词**筛选；时间倒序分页。
- **实时日志流**：SSE 推送，边跑边看 —— 装依赖时能实时看到子进程输出。
- 关键词 / 正则搜索，命中高亮。
- 单条详情：完整堆栈、上下文 JSON、所属作业与请求。
- **错误 ↔ 作业日志双向跳转**。

**traceId 贯通（这一条是灵魂）**

- 每个 API 请求、每个作业都生成唯一 `traceId`。
- 错误提示（Toast / 弹窗）上直接显示 **错误码 + traceId**，并带「查看日志」按钮；点击后**自动按该 traceId 筛选**，一步跳到现场。
- 没有这一条，"查看日志"就只是把文件搬到界面上而已。

**崩溃与兜底**

- 主进程未捕获异常、渲染进程崩溃（`render-process-gone`）、窗口无响应 → 记录日志 + 提示 + 可一键导出。
- **白屏兜底**：前端启动失败时展示降级页面（内含日志入口），而不是一片空白。

**保留与轮转**

- 结构化日志落库 `app_logs` 表；同时写文本文件，便于崩溃后仍能完整取出、整包发送。
- 默认保留 30 天；文件按大小 / 天数轮转，超出自动清理；设置里可改。
- 提供「清理日志」按钮。

**脱敏（强制，不可关闭）**

- 写入前统一过滤：**Bearer Token、PAT、密码、Cookie** 一律替换为 `***`。
- 工作区外绝对路径中的用户名替换为 `%USER%`（可配置开关）。
- **绝不允许把 GitLab / GitHub 的令牌写进日志。**

**导出诊断包**

一键导出 ZIP：最近日志（已脱敏）+ 环境快照（工具链版本）+ 应用版本 + 数据库 schema 版本 + 工作区结构摘要（仅相对路径）。**不含任何项目正文数据**，可直接发给他人求助。

## 10. 风险登记

| 风险 | 应对 |
|---|---|
| 官方脚手架参数随版本变化，某天突然不可用 | 版本检测 + 失败自动回退内置模板 |
| 联网失败 / 镜像源不可用 | 允许跳过安装，并给出可复制的手动命令 |
| 自动修改 PATH 影响整机 | 只追加不覆盖、改前备份、一键回滚、逐项可勾选 |
| 工作区迁移中途中断或文件被占用 | 预检 + 复制校验后才删 + 原目录兜底 + 可取消 |
| 数据库位于工作区内，迁移时被占用 | 迁移前 checkpoint 并关闭连接，连 `-wal` / `-shm` 一并处理 |
| 命令执行被利用为后门 | 命令白名单、参数模板化、禁止模板携带任意脚本、路径越界校验 |
| 长任务期间用户关闭窗口 | 关闭 = 最小化到托盘；托盘「退出」时二次确认 |
| 便携工作区拷贝到另一台机器后路径失效 | 启动时检测路径有效性并提示重新定位 |
| 日志泄露令牌 / 密码等敏感信息 | 写入前**强制脱敏**（Token / PAT / 密码 / Cookie），不可关闭；脱敏函数单测覆盖 |
| 日志无限增长撑爆工作区 | 默认保留 30 天 + 按大小与天数轮转 + 手动清理入口；文本日志单文件 5 MB、保留 5 份 |
| 高频日志拖慢主流程 | 内存缓冲批量落库（500ms / 200 条），文本文件同步落盘兜底 |

## 13. 下一版本待办（应用 v0.2）

### 13.1 工作区边界：工作区只放用户数据，配置与运行期产物一律移出

**要求（2026-09-22，用户提出）**：工作区应当是**单独的区间**；各种**配置项不要放在工作区里**。

> **状态：✅ 已在 0.1.1 实施**（2026-09-23）。实施内容与验证证据见技术设计 §18；
> 下面「实施要点」保留为当时的计划，实际做法以 §18 为准。

**用户已确认的模型**：一个工作区里放**多个项目**，每个项目**自带完整一套、互不共享**；
应用自身的配置与运行期产物一律移出工作区（即下面这张表）。

**目标归属**

| 归属 | 内容 | 是否随工作区被拷走 |
|---|---|---|
| **工作区**（自包含、可整体拷走即迁移） | 项目 / 任务 / 标签 / 里程碑 / 依赖 / 工作流状态等**业务数据**（`workspace.db`）、各项目代码目录（`projects/`）、附件（`attachments/`） | 是 —— 这正是"便携包"的含义 |
| **AppData**（应用自身的区域） | 全局配置与工作区清单（`config.json`）、**应用运行日志**、**作业日志**、**备份**、缓存 | 否 |

**现状审计（2026-09-22 实测，逐个核对过）**

| 项 | 现状 | 结论 |
|---|---|---|
| `<userData>/config.json` | 主题 / 偏好 / 工作区清单都在这里 | ✅ **已符合**（这条不要动） |
| 工作区数据库里的 `app_logs` 表 | 实测 **452 行** —— **应用自身的运行日志正混在用户数据里** | ❌ 移出：并入 AppData 的日志（已有 `<userData>/logs/main.log` 文件 + 轮转） |
| 工作区里的 `logs/jobs/` 目录 | `ensureWorkspaceLayout` 建了它，但**没有任何代码往里写**（作业日志实际写进 DB 的 `job_logs` 表） | ❌ 冗余：删掉，或把作业日志真正落成文件 |
| 工作区里的 `backups/` 目录 | 建了但为空（自动备份**只有配置项、没有实现**） | ❌ **自指**：备份放在被备份对象内部，整体拷贝 / 迁移时会滚雪球。移到 AppData 或用户指定目录 |
| `workspace_meta` 表 | 建表迁移里有，**没有任何代码读写**（0 行） | ⚠️ 定死语义：只放"工作区自身的元数据"（格式版本、迁移标记），**不放应用配置**；做不到就删表 |
| `attachments/`、`projects/` | 建了但为空（M3 / M4 才会写入） | ✅ 保留在工作区内（属于用户数据，是"便携包"的必要组成） |

1. 把日志存储（`LogStore`）从"写入工作区数据库"改为写入 **AppData 下的独立库**（或直接走文件 sink）。

2. `ensureWorkspaceLayout` 不再创建 `backups/` 与 `logs/jobs/`；工作区结构收敛为
   `workspace.db + projects/ + attachments/`。
3. 备份路径可配置（默认 AppData），并明确"备份不随工作区迁走"。
4. **老工作区兼容**：目录/表结构变更是破坏性变更，需要"打开旧工作区时自动整理"，或至少给出明显提示；
   这块与 M5（工作区迁移）一起做，别单独动。
5. 文档同步：§4.3 的结构图在实施后要改掉。

**下一版本开工前需先定（三个开放问题）**

1. 老工作区里已有的 `app_logs` 数据（你机器上现有 452 行）—— 保留、导出，还是直接丢弃？
2. 备份放哪：AppData 固定目录，还是让用户指定（后者更贴合"备份到别处"的诉求）？

### 13.2 项目之间"互不共享"：现状例外与要收的口子

用户确认的规则：**一个工作区里放多个项目，每个项目自带完整一套、互不共享**。
按这条去核对现状，发现**已有的两处跨项目共享**与它冲突 —— 这类"设计里的共享点"如果不专门清掉，
后面会一直有"为什么隔壁项目的标签出现在我这儿"的困惑。

| 项 | 现状（实测） | 与规则的关系 | 下一版本怎么处理 |
|---|---|---|---|
| **全局标签** | `tags.project_id` **可为 NULL**，NULL 即全局标签；项目视图的标签接口返回**项目标签 + 全局标签**（`or(eq(project_id), isNull(project_id))`） | ❌ 直接违反"互不共享" | ✅ **已完成（2026-09-26，迁移 `0006`）**：`project_id` 改 NOT NULL、删掉 `/tags` 全局接口与 `listTags` 的 `globalOnly` 分支、查询条件改回纯 `eq`、唯一索引改成 `(project_id, name)`。实施记录与"改老表"的坑见 technical-design §37 |
| **全局工单类型** | `ticket_types.project_id` 同样可为 NULL（工单功能 M3 才落地） | ❌ 同上，但**目前没有数据、也没有界面** | ✅ **已完成（同一条 `0006` 迁移）**：同样改成 NOT NULL |
| **作业（`jobs`）没有项目字段** | `jobs` 表只有 `type/title/status/...`，`scaffold`、`backup` 这类作业**无法按项目过滤**；项目信息只可能藏在 `payload_json` 里 | ⚠️ 作业列表天然变成"全工作区混在一起" | 加 `project_id`（可空，工作区级作业如 `workspace-migrate`/`backup` 留空），作业页默认按当前项目过滤 |
| **附件目录布局** | `attachments/` 目录已建但为空（M3 才写入） | ✅ **已定（0.1.2 起 + 2026-09-26 确认）**：一个项目一个文件夹，附件落在**项目文件夹内**的 `attachments/`（`<工作区>/<项目文件夹>/attachments/`），不是工作区根下的 `attachments/<projectId>/`。用户 2026-09-26 明确：「附件存在自己的项目中，比如前端的图片是保存在他项目内的」。这样附件天然跟着项目走，项目文件夹被搬走时附件一起走 | ⚠️ M3 实现附件时**必须复用"搬项目文件夹"那套路径解析**，不能自己拼绝对路径，否则"更改工作区目录"之后附件会全部断链；另见 §5.4.1 的 `.gitignore` 与"文件被手动删掉"两个坑 |
| 工作流状态 / 里程碑 / 任务 / 依赖 | 状态、里程碑、任务都是 `project_id` **非空**；依赖表本身没有 project_id，但服务层**显式校验两端同项目**，跨项目直接报错 | ✅ 已符合 | 不动 |
| `activity_logs.project_id` 可空 | 可空用于承载**工作区级**操作（如工作区迁移） | ✅ 合理 | 保留：项目级事件必须带 project_id，工作区级事件才允许为空 |
